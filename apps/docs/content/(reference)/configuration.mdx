Every setting lives under `CacheTags`. You can add targets in the backoffice instead, and the other settings have defaults that suit most sites.

<CodeGroup>
```json appsettings.json
{
  "CacheTags": {
    "Targets": {
      "nextjs": { "Url": "https://www.example.com/api/cache-tags", "Secret": "<at least 32 characters>" }
    }
  }
}
```

```sh Environment variables
CacheTags__Targets__nextjs__Url=https://www.example.com/api/cache-tags
CacheTags__Targets__nextjs__Secret=<at least 32 characters>
```
</CodeGroup>

## Settings

| Setting | Default | What it does |
| --- | --- | --- |
| `Enabled` | `true` | Whether the package tags responses and plans and sends purges. |
| `Targets` | none | Where the package sends purges, by name. See [Purge targets](/targets). With none, the package still plans and records changes. |
| `Secrets` | none | Secrets that targets added in the backoffice read by name, such as `CacheTags:Secrets:VercelSecret`. A target can read nothing else from configuration. See [Purge targets](/targets#in-the-backoffice). |
| `AllowPrivateNetworkTargets` | `false` | Lets targets added in the backoffice connect to private and reserved addresses, such as `localhost`. See [Purge targets](/targets#in-the-backoffice). |
| `HeaderName` | `X-Umbraco-Cache-Keys` | The response header that carries the keys. `Cache-Tag` for Cloudflare in front of Umbraco. |
| `KeyPrefix` | none | A prefix for every key, such as `shop-`, for a site that shares a CDN zone with another. Lowercase letters, digits and hyphens, ending in a hyphen. |
| `MaxHeaderKeys` | `128` | The most keys a header lists, most needed first, at least 2. 128 is Next.js's limit per cache entry. Raise it when Cloudflare caches the Delivery API directly. See [Cloudflare](/cloudflare#in-front-of-the-delivery-api). |
| `KeySets` | `true` | Whether a response showing more items than its header lists carries one stored `set-` key for them, so only a change to one of its own items purges it. Off, it carries their `type-` keys. See [Limits](/keys#limits). |

The timings are fixed. [How a purge is timed](/timing#at-a-glance) lists them.

## Target settings

| Setting | Default | What it does |
| --- | --- | --- |
| `Type` | `webhook` | `webhook`, `cloudflare`, or the type of a target you registered. |
| `Enabled` | `true` | Whether the package sends purges to this target. |
| `Url` | none | For a webhook, where the package posts purges. https, except on localhost. |
| `Secret` | none | For a webhook, the signing secret, at least 32 characters. |
| `Headers` | none | For a webhook, request headers to send with every purge. See [Purge targets](/targets#request-headers). |
| `Settings` | none | Settings for other types, such as Cloudflare's `ZoneId` and `ApiToken`. |
| `Roots` | none | For an Umbraco with several sites: the keys of every root whose content this target's frontend shows, including shared roots it picks from. Changes under other roots only are not sent to it. Can also be set in the backoffice. See [Purge targets](/targets#several-sites). |

:::caution
Keep secrets and tokens out of `appsettings.json` in source control. Set them as environment variables, such as `CacheTags__Targets__nextjs__Secret`, or in your host's secret store.
:::

## Removing the package

Put your frontend back on a revalidate timer first, since purges stop. Then set `Enabled` to `false` to stop tagging and purging while the package is still installed.

Uninstalling the NuGet package leaves its data behind: the tables whose names start with `theBuilderCacheTags`, its row in `umbracoLock`, and its migration state, the `Umbraco.Core.Upgrader.State+TheBuilder.CacheTags` row in `umbracoKeyValue`. Remove all three by hand once no server runs the package. A migration state left behind stops a later install from creating the tables again.
