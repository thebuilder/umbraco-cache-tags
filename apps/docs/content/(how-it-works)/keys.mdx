Every key is lowercase ASCII, because Cloudflare matches tags case-insensitively and Next.js case-sensitively.

| Key | Covers | Purged as |
| --- | --- | --- |
| `content-<guid>` | One document | expire |
| `media-<guid>` | One media item | expire |
| `type-<alias>` | Every listing filtered by a content or media type | stale |
| `type-<alias>-<root>` | The same, for listings inside one site root. See [Several sites](#several-sites) | stale |
| `children-<guid>` | Every listing of a parent's children (`fetch=children:`) | stale |
| `search-<index>` | Every other query against an index, such as a search | stale |
| `search-<index>-<root>` | The same, for queries inside one site root | stale |
| `x-<name>` | Whatever a site's own API names. See [Your own APIs](/your-apis) | expire |
| `set-<hash>` | A stored set of items, for a response that shows too many to list. See [Limits](#limits) | expire |
| `umbraco` | Everything | stale |

"Expire" means the next request waits for fresh content. "Stale" means the next request may get the old response once while it refreshes. Listings and site-wide changes touch many pages, and listings only change once the index has caught up.

## What a response carries

A response carries the keys of what it shows:

```http
X-Umbraco-Cache-Keys: umbraco, content-e000...0003, content-e000...0004
```

That is `umbraco`, the listing keys that select the response, any `x-` keys, and the `content-` and `media-` keys of the items it shows, the items it links to and the media it uses. [How keys are collected](/collection) shows which items count, and how `expand`, links and rich text change that. A listing carries its listing key too:

```http
X-Umbraco-Cache-Keys: umbraco, children-e000...0001, content-e000...0003, content-e000...0004
```

When content changes, the package plans the change as keys and purges them. A cached response is reached by the keys it carries, so a purge reaches every copy of it, however long it has been cached. Nothing else has to be stored or looked up for that to hold, except for a response that shows too many items to list (see [Limits](#limits)).

## Catch-all listings

Some listings can change with any publish:

- a listing selected by a search, a name filter, or any filter other than a content type
- a listing with no parent or content type to select it, such as all descendants of a path
- a `fetch` of an item that does not exist yet, by path or by id
- a content type filter naming a type that does not exist, or more than 2 types

They carry the catch-all `search-` key, and every publish plans it, which purges all of them at once:

```http
X-Umbraco-Cache-Keys: umbraco, search-deliveryapicontentindex, content-e000...
```

A request for items by id (`items?id=`) carries the key of every id asked for, so publishing one that did not exist yet reaches it.

## Several sites

An Umbraco with several sites has a root for each, a document at the top of the content tree. A listing fetched from inside a root can only show that root's content, so its `type-` and `search-` keys are scoped to the root:

```http
GET /umbraco/delivery/api/v2/content?fetch=descendants:/guides/&filter=contentType:guidePage
X-Umbraco-Cache-Keys: umbraco, type-guidepage-e000...0001, content-e000...0012, ...
```

A change to a document plans the global keys and its own root's. Publishing a guide in Site A purges:

| A cached response on Site B | Purged? |
| --- | --- |
| A listing inside Site B's root, such as `fetch=descendants:` filtered by type | No, it carries Site B's scoped keys |
| A listing across every root, such as a search or a type filter with no `fetch` | Yes, it carries the global keys |
| A page that picks or links that guide | Yes, it carries the guide's own `content-` key |

A move between roots plans both roots' keys. The types a response lists in place of its items (see [Limits](#limits)) are scoped to each item's root too. `children-` keys name a parent and item keys an item, so they never needed scoping, and media has no roots, so media keys stay global.

This keeps one site's edits from emptying another site's listings. To also keep the purge requests themselves away from another site's frontend, limit each target to its roots (see [Purge targets](/targets#several-sites)).

## What a change purges

A publish purges the item's own key, its parent's `children-` key, its type's `type-` keys and the `search-` keys, globally and for its root. A move also purges the old parent's `children-` key. A change to an item's URL, such as a move, a rename or an unpublish, also purges its descendants, since their URLs change with it. These reach further:

| Change | Purges |
| --- | --- |
| Domain, language or public access | `umbraco`, as stale |
| Content type, media type or data type | `umbraco`, as stale, since any response may render an item of the type |
| A route change with more than 500 descendants | `umbraco`, as stale |
| Content type alias rename | `umbraco`, and again the old and new alias's listings once every index has the new alias, up to a minute later |
| Sort | The parent's `children-` listings, the sorted items' `type-` listings and every `search-` listing, once every index has the new order |

## Which responses get keys

| Response | Gets |
| --- | --- |
| Cacheable (200) | Its keys |
| Preview | `no-store` and no keys |
| From a signed-in member or backoffice user | `private` and no keys |
| Anything else, such as not found and redirects | `no-store` and no keys, because no item covers them and no purge would reach them |

## How long a response may be cached

As long as you like. A purge reaches a cached response by the keys it carries, so a long lifetime only matters for a purge that never arrives, such as one to a target that stayed down. In Next.js, `cacheLife("days")` or `cacheLife("weeks")` is a sensible safety net.

## Limits

Next.js keeps at most 128 tags per entry, each at most 256 characters, and drops the rest. A header lists at most `MaxHeaderKeys` (128) keys, with the keys purges need first: `umbraco`, its listing keys, its `x-` keys, then its item keys. Umbraco's own output cache has no limit and keeps every key.

Past 64 items, or when the items would push the header past its limit, a response carries one `set-` key in their place. The package stores which items the set holds, in the Umbraco database, and a change to any of them purges the set too. A landing page linking 80 articles is then purged when one of those articles changes, not on every article publish.

```http
X-Umbraco-Cache-Keys: umbraco, set-3f9a0c1d2e4b5a6978c0d1e2f3a4b5c6
```

| Response | Carries |
| --- | --- |
| 12 items | `umbraco`, its listing keys, 12 `content-` keys |
| 80 linked articles | `umbraco`, its listing keys, `set-3f9a…` |
| 80 linked articles, set not stored in time | `umbraco`, its listing keys, `type-article` |
| A listing of 80 items | `umbraco`, its listing keys, their `type-` keys |

A listing lists its items' types, not a set: its listing key already reaches it when an item joins or leaves, and every page and filter of a listing would need a set of its own. Responses that show the same items share one set, so rendering a page again stores nothing new.

<Expandable title="When a set isn't stored">
A response carries a `set-` key only once its set is stored. When the database is slow or failing, or a server has stored 100 new sets in the last minute, the response carries its items' `type-` keys instead. Every change to an item purges its `type-` key, so such a response is still reached, only more often. The log warns once a minute with how many responses missed the time limit.

A set no server has rendered for 90 days is removed and purged, so a response cached longer than that renders again rather than going stale. Turn sets off with `CacheTags:KeySets` to keep everything out of the database.
</Expandable>

:::caution
A full header is about 6 KB, more than some proxies allow by default. See [Go live](/go-live#what-your-setup-needs).
:::
